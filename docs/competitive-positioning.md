# Competitive Positioning

**Review date:** 2026-08-28

This document is a positioning guide, not a permanent claim about competitors. Revalidate external projects before publishing comparisons.

## Category

SpecGrain belongs to the emerging space between spec-driven development, coding-agent orchestration, and software delivery governance.

## GitHub Spec Kit

Reference: <https://github.com/github/spec-kit>

Spec Kit is a major upstream influence and compatibility target. It popularized a structured `specify -> plan -> tasks -> implement` style of spec-driven development and supports many coding-agent integrations.

SpecGrain should not compete by cloning its command set. The design departure is recursive refinement: a spec may become smaller specs repeatedly until executable Grain readiness is satisfied. Execution evidence and context budgeting are core data, not afterthoughts.

## OpenSpec

Reference: <https://github.com/Fission-AI/OpenSpec>

OpenSpec emphasizes lightweight, iterative spec-driven workflows. SpecGrain should differentiate through a deterministic recursive domain model, readiness contracts, evidence binding, and measurable delivery-process quality rather than simply offering another document workflow.

## BMAD Method

Reference: <https://github.com/bmad-code-org/BMAD-METHOD>

BMAD provides broad role/workflow coverage for AI-assisted development. SpecGrain should avoid persona proliferation. Its roles are protocol responsibilities: shape, execute, verify, control. The same human or model may fill different responsibilities in isolated contexts.

## Kiro

Reference: <https://kiro.dev/>

Kiro combines spec-driven features with an integrated agent product. SpecGrain's opportunity is portability: repository-native specs, deterministic control, open evidence, and adapters that do not require one IDE or hosted service.

## OpenAgile.AI

Reference: <https://openagile.ai/>

OpenAgile.AI demonstrates that hierarchy decomposition, atomic tasks, scoped context, and isolated execution are already active competitive ideas. Therefore these features alone are not sufficient differentiation.

SpecGrain's stronger thesis is one recursive spec primitive plus deterministic Grain readiness, evidence binding, method routing, context accounting, and delivery-process measurement.

## AgileSpec

Reference: <https://agilespec.org/>

AgileSpec occupies adjacent naming and methodology territory. SpecGrain should not position itself as "Agile plus specs." Agile is one source of delivery principles, while SpecGrain's brand and architecture center on granularity and proof.

## Positioning statement

> SpecGrain is the open, agent-neutral control plane that recursively refines software intent until every executable change is small enough to understand, contextually isolate, verify, recover, and prove.

## What must remain uniquely strong

1. **One recursive spec primitive.** No required epic/story/task ontology.
2. **Grain as a computed readiness property.** "Atomic" is not a label an agent may assign casually.
3. **Context as an engineering budget.** Required context can invalidate readiness.
4. **Independent evidence.** Completion state is bound to exact spec and implementation revisions.
5. **Change-surface control.** Unscoped modifications become first-class verification failures.
6. **Method proportionality.** Quick, DMAIC-lite, DMADV-lite, experiment, and controlled profiles add only useful gates.
7. **Process analytics.** Measure rework, first-pass verification, cycle time, drift, context efficiency, and scope accuracy.
8. **Open migration path.** Existing Spec Kit and other structured workflows can be imported rather than discarded.

## Competitive rule

Do not publish claims such as "faster," "safer," "lower token cost," or "better than Spec Kit" until SpecGrainBench reproduces the claim under controlled conditions.
